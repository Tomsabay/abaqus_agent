# cantilever — the reference case

A 100 × 10 × 10 mm steel cantilever, fixed at one end, pulled down by a 1 N
point load at the other. It is the smallest case in this repository that
exercises the whole pipeline, and it is the one every other claim is checked
against, so it is worth knowing exactly what it asserts and why.

```
spec.yaml        the problem statement (geometry, material, step, KPIs)
expected.json    the frozen baseline the run is graded against
runner.json      solver resources (cpus, mp mode, timeout)
contracts.yaml   physics contracts evaluated on the extracted KPIs
```

Run it:

```bash
python agent/orchestrator.py cases/cantilever/spec.yaml \
  cases/cantilever/expected.json \
  cases/cantilever/runner.json
```

The backend is chosen automatically — Abaqus if installed, CalculiX otherwise.
This is the one case the CalculiX subset covers in full.

## The baseline, and where the numbers come from

| KPI | Frozen value | rtol | atol |
|---|---|---|---|
| `U_tip` | `-1.9039579201489687e-3` mm | 0.10 | 1e-6 |
| `MISES_MAX` | `0.6528551578521729` MPa | 0.20 | 0.01 |

`U_tip` is checkable by hand, which is the entire reason this case leads. For
a cantilever with an end load, Euler–Bernoulli gives

```
δ = P·L³ / (3·E·I)     I = W·H³/12 = 10 · 10³ / 12 = 833.33 mm⁴
  = 1 · 100³ / (3 · 210000 · 833.33)
  = 1.9048e-3 mm
```

The solver returns `1.9039579e-3` mm — **0.04% from the closed-form answer**.
That agreement is the evidence that a real solve happened and that the model
means what the spec says; no screenshot of a log file is as convincing, and
none is needed.

CalculiX 2.23 returns `-1.903958e-3` mm on the same deck: the two solvers
agree to seven significant figures.

`MISES_MAX` is *not* cross-checkable that way. Abaqus reports unaveraged
`ELEMENT_NODAL` stress; CalculiX reports nodal-averaged stress from its `.frd`.
On this mesh they differ by about 6%, so the CalculiX number is tagged with its
provenance and excluded from pass/fail rather than graded against an Abaqus
baseline it does not mean the same thing as.

## Why C3D20R

The element type is pinned to **C3D20R** (quadratic, reduced-integration
hexahedron) and the mesh seed to 5.0 mm. That combination gives only 2 × 2 × 20
elements, which matters:

- A linear reduced-integration element (C3D8R) at this coarseness suffers shear
  locking and hourglassing in bending. An earlier baseline measured
  `-2.5716e-3` mm — about 35% off the closed-form answer. A case whose headline
  claim is "it agrees with theory" cannot be built on that.
- A quadratic element captures the linear strain gradient through the
  thickness, so a coarse mesh is legitimate here rather than merely cheap.

Changing the element type and the mesh size at the same time is forbidden by
convention in this repository: if the number moves you would not know which
change moved it.

`tests/test_cantilever_baseline_freeze.py` asserts the values above. Widening
`rtol` to make a failing run pass is not an acceptable fix — if the number
moves, either the model changed or something is wrong, and both deserve to be
found rather than absorbed by a tolerance.

## Run directories

A run directory is named `sha256(canonical spec)[:16]`, so any edit to
`spec.yaml` — including a field with no physical meaning, like the targeted
Abaqus release — produces a new directory. Old directories are never
regenerated by a later run. They are kept as evidence and should not be
deleted casually.

CalculiX runs get a `-ccx` suffix so they cannot overwrite an Abaqus baseline.
